# 更新需求登记模板

> 用途：把下一批要做的改动按统一格式登记给我（贴到对话里或直接改本文件都可以）。
> 填写要点在每节末尾的「填写提示」里；不确定的字段留空或写「待定」，我会在动手前先问清楚。

---

## 一、单条需求模板（复制这一段）

```markdown
### 需求：<一句话标题>
- 编号：REQ-<年月>-<序号>（如 REQ-202612-01，可留空）
- 优先级：P0 紧急 / P1 重要 / P2 一般（默认 P2）
- 期望版本：（如 v4.1.7，可留空由我安排）
- 提出日期：YYYY-MM-DD
- 类型：新增功能 / 功能改进 / 缺陷修复 / 性能优化 / 权限调整 / 文档

**1. 背景与目标**
为什么要做，解决什么问题；期望的结果用一两句话描述。

**2. 涉及范围**
- 页面 / 模块：（如 使用人员、报废记录、机柜视图）
- 角色 / 权限：（哪些角色要用；是否需要新权限点）
- 是否涉及导出 / 导入：（是 → 列名怎么变）
- 是否涉及接口：（是 → 新接口 or 改现有接口）

**3. 具体变更（按用户视角描述）**
1. ……
2. ……

**4. 数据与约束**
- 字段 / 表格：（新增字段？表结构要改吗）
- 校验规则：（必填、长度、唯一、上限）
- 历史数据：（存量数据怎么处理；要不要迁移脚本）
- 是否可删除数据：（删除是真删除还是标记作废，是否需要留痕）

**5. 验收标准**
1. ……
2. ……

**6. 未定事项（我来问）**
- ……

**7. 参考**
截图 / 现有页面 / 竞品做法 / 相关文档链接。
```

**填写提示**
- 「具体变更」按**用户点哪里、看到什么**来写，不用写技术实现；
- 「数据与约束」只要写到字段/规则/历史数据处理，实现方式我来定；
- 涉及删除、批量操作、权限变更的，务必写清「谁能做」「要不要留痕」；
- 一条需求只做一件事，跨多个页面的改动拆成多条，方便分批发布。

## 三、示例（已实现的需求，照着写即可）

```markdown
### 需求：报废记录支持编辑备注与删除
- 编号：REQ-202611-05
- 优先级：P1
- 期望版本：v4.1.6
- 提出日期：2026-11-18
- 类型：功能改进

**1. 背景与目标**
报废记录录入后备注填错无法修改，误录的记录也无法清理；希望能更正备注并删除错误记录。

**2. 涉及范围**
- 页面 / 模块：报废记录
- 角色 / 权限：需要「报废管理」的修改/删除权限，只读账号不可用
- 是否涉及导出 / 导入：导出列不变
- 是否涉及接口：新增编辑与删除接口

**3. 具体变更**
1. 列表操作列新增「编辑备注」「删除」两个按钮；
2. 编辑只允许改备注，最多 500 字；
3. 删除前二次确认，删除后列表立即刷新。

**4. 数据与约束**
- 只改 `asset_scrap_record.notes`，不新增字段；
- 删除为真删除；操作日志要记录删除人、设备名、原因、报废时间和备注。

**5. 验收标准**
1. 改完备注刷新后仍然是新备注；
2. 删除后列表与导出都不再出现该记录；
3. 只读账号点击按钮应被拒绝（403）。

**6. 未定事项**
- 无

**7. 参考**
报废记录页面截图。
```

## 四、版本与节奏约定（当前沿用）

| 环节 | 约定 |
| --- | --- |
| 提需求 | 用本模板登记，我按优先级排进下一个版本 |
| 动手前 | 有未定事项我先一次问清，避免返工 |
| 实现后 | 本地跑接口 + 前端构建 + 252 项回归，给出验证结果 |
| 发布 | 递增补丁版本（v4.x.y），更新说明只写使用者能感知的变化 |
| 部署 | 你在「设置 → 系统更新」点更新；数据库迁移随部署自动执行 |

## 五、容易漏写的几点（提需求时先自查）

- [ ] 谁能用（角色/权限），谁不能用
- [ ] 数据错了要不要能改、能删，删了要不要留痕
- [ ] 导出/导入的列名或顺序是否变化
- [ ] 历史数据要不要迁移，旧数据怎么显示
- [ ] 有没有数量上限（比如备注 500 字、单次导入 2000 行）
- [ ] 是否需要和现有功能联动（例如删除后释放设备、改状态后自动退回分配）
