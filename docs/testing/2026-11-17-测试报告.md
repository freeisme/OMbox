## 6. 性能测试

### 6.1 单请求基线（串行）

| 接口 | 平均耗时 |
| --- | --- |
| `GET /api/state?include=computers` | **1374 ms** |
| `GET /api/tickets` | **1435 ms** |
| `POST /api/auth/login` | 987 ms |
| `POST /api/exports/xlsx`（200 行） | 836 ms（5.4 KB） |

### 6.2 并发

| 场景 | 并发 | 吞吐 | p50 | p95 | 错误 |
| --- | --- | --- | --- | --- | --- |
| `/api/state` | 8×10 | 1.4 rps | 5770 ms | 6171 ms | 0 |
| `/api/state` | 16×12 | 1.2 rps | 12875 ms | 14335 ms | 0 |
| `/api/tickets` | 8×10 | 2.7 rps | 2825 ms | 3181 ms | 0 |

**PERF-01（高）**：并发从 8 提到 16，吞吐几乎不变（1.4 → 1.2 rps），说明请求几乎完全排队。
根因：数据库访问通过 **每条查询启动一个 `mysql` CLI 子进程** 实现（`run_mysql` / `run_mysql_rows`），单请求要跑多次查询，进程创建 + CLI 握手开销主导耗时；GIL 与进程创建争用进一步放大排队。

建议（按性价比）：
1. 单请求内合并查询：`/api/state` 用 `JSON_OBJECTAGG`/多结果集一次取回；
2. 读多写少的字典类数据（模块、角色、组织树）加进程内 TTL 缓存；
3. 中期引入连接池（如内置 `pymysql` 随包分发，避免生产装 PyPI）。

### 6.3 优化后（v4.1.4）

针对 PERF-01 做了两处**不改变语义**的缓存，均可在写请求时立刻失效：

1. **会话上下文缓存**（`OA_AUTH_CONTEXT_TTL`，默认 20 s）：同一令牌在窗口内复用"会话校验 + 用户/员工/组织"的查询结果，续期仍按 60 s 节流写库；
2. **状态快照缓存**（`OA_STATE_CACHE_TTL`，默认 3 s）：`build_state_payload()` 与用户无关，整包复用；权限裁剪仍逐请求执行，因此不会串号。

| 场景 | 优化前 | 优化后 | 提升 |
| --- | --- | --- | --- |
| `/api/state` 单请求 | 1374 ms | **519 ms** | 2.6× |
| `/api/state` 8 并发 | 1.4 rps / p50 5770 ms | **7.9 rps / p50 769 ms** | 吞吐 5.6×，延迟 7.5× |
| `/api/state` 16 并发 | 1.2 rps / p50 12875 ms | **9.4 rps / p50 1332 ms** | 吞吐 7.8×，延迟 9.7× |
| `/api/tickets` 8 并发 | 2.7 rps / p50 2825 ms | 3.2 rps / p50 2385 ms | 小幅 |

服务端分段耗时（`OA_STATE_TRACE=1`）：首次请求 auth 414–516 ms / build 134–154 ms / filter 570–805 ms；缓存命中后三者均为 **0 ms**。

仍存在的瓶颈（下一步）：
- `/api/tickets` 单请求约 1.2 s，16 并发 p50 4.7 s，尚未接入缓存；
- 缓存失效为"写请求全清"，写入频繁时命中率会下降，可改为按资源类型定向失效。

**安全注意**：登出会立即清除该令牌的上下文缓存；任何写请求会清空上下文与快照缓存，因此权限变更、组织调整都不会被旧缓存拖延。

## 8. 缺陷与风险

| 编号 | 级别 | 描述 | 状态 |
| --- | --- | --- | --- |
| BUG-01 | 高 | 工控机扫描传非法网段时 `ipaddress.AddressValueError` 冒泡成 **500 + 服务端 traceback** | ✅ 已修（捕获 ValueError → 400） |
| BUG-02 | 中 | `/api/access-control` 对只读账号返回**全公司账号清单** | ✅ 已修（`users` 仅 `user_management:update` 返回） |
| RISK-01 | 中 | 测试库中 `viewer` 角色拥有 `user_management/role_management/system_updates` 的查看权，与种子脚本 `20260817_001_access_control.sql`（第 172-173 行明确排除）不符 | ✅ 已修（迁移 `20261117_001_viewer_least_privilege.sql`，viewer 可查看权限 156→138；实测该账号读 `/api/access-control` 返回 403、`users` 为空） |
| PERF-01 | 高 | 单请求 1.4 s，并发不提升吞吐（每条查询一个 mysql 子进程） | ✅ 已优化（见 6.3，并发吞吐 8×） |
| QUAL-01 | 低 | pyflakes 12 条（未使用导入/变量） | ⏳ 可随手清理 |

RISK-01 回收 SQL（确认后执行，注意会同时收回系统更新入口）：

```sql
UPDATE auth_role_permission rp
JOIN auth_role r ON r.role_id = rp.role_id
JOIN auth_permission p ON p.permission_id = rp.permission_id
SET rp.can_view = 0, rp.can_export = 0
WHERE r.role_code = 'viewer'
  AND p.module_code IN ('user_management', 'role_management', 'system_updates');
```

## 9. 复现方式

```bash
# 1) 起服务（务必指向测试库）
SERVER_PORT=8030 DB_NAME=ombox_v405_test python server.py

# 2) 跑黑盒/安全/兼容/性能套件
python tests/qa/http_suite.py --base http://127.0.0.1:8030
python tests/qa/http_suite.py --base http://127.0.0.1:8030 --no-perf   # 跳过压测

# 3) 单元回归 + 覆盖率
python -m unittest tests.test_regressions
python -m coverage run --branch --source=office_asset,server -m unittest tests.test_regressions
python -m coverage report
```

> 套件只创建 `QA-` 前缀的办公终端并在末尾删除，不修改表结构；性能段使用 `compa` 账号，避免安全段的失败登录把 `admin` 锁住。
